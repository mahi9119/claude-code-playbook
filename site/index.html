Measured against the private repository on 22 October 2026. The product is deployed and pre-launch, with no paying clients yet. 162 database migrations, 30 guard tests, 30 decision records, 22 project skills.

The product is the evidence. The method is the argument.

The product is a B2B SaaS that handles invoices, contracts and compliance for its customers. Money is computed with exact decimals, every tenant's data is isolated by the database itself, and every financial change writes an audit row. That is a lot of rules for a small team to hold in their heads, and an AI agent holds none of them between sessions.

So we stopped relying on anyone remembering. Claude Code wrote most of the keystrokes. We wrote the rules it works under, the scripts that enforce them, and the reviews that check its work. This page is about that layer.

The one idea

A rule that lives only in a document holds until the day it matters.

Every mistake in the project goes through the same four steps, and the fourth is what makes the rest stick.

  1. IncidentSomething breaks, or nearly does. It gets a number in the tracker before anyone touches a file.
  2. LessonWritten into the lessons log in the same turn, with the guard named, or the word "judgment" and the reason.
  3. GuardA test, script or hook that fails loudly on a repeat. Proven red on the broken code before it is trusted.
  4. RecallA session-start hook puts the lesson index in front of every new Claude session, so even unguarded lessons are read.

The method

Nine rules, each with the incident that made it.

The reason is written next to every rule in the project constitution, so nobody tidies a rule away without knowing why it exists.

Use it

Everything here is generic and MIT licensed.

Copy the constitution, cut it down to your project, and add guards as your own incidents earn them. Do not install every guard on day one.

Principles that hold it together

  • Blocking but narrow beats advisory but broad. New guards bind new work from day one and grandfather the old, one file at a time.
  • Cheap checks first. Lint before the database suite, the suite before the build, code review before a browser session.
  • A skipped test is not a passing test. Report passes, skips and failures separately, every time.
  • Prove the guard can fail. Break the code, watch the guard go red, restore. A guard that has never been red has never been tested.
  • A process exception is not a judgement exception. "Ship it yourself overnight" removes the wait between steps, not the owner's decisions.
